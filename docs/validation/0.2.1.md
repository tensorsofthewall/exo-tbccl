## Behavior at default settings

On the 27-billion-parameter run the default TBCCL decode median was about 5% slower than exo's MlxRing backend (about 146 versus 139 ms per token); with the opt-in Metal activity policy it was 1 to 4 ms per token faster. Decode there is bound by the Mac's memory bandwidth, not the link (about 30 KB per token). First-token output matched the control except for a documented bf16 near-tie, which flips run to run even under MlxRing; the transport itself was bit-exact.

## Provenance and gaps

- The real two-host runs were recorded against an earlier TBCCL wire protocol (3). The unit and loopback suites were re-run after the move to wire protocol 4; the physical exo runs were **not** repeated.
- One integration defect was found and fixed in the exo glue (not in exo-tbccl or TBCCL): exo nodes never exited after an `MlxTbccl` instance because the runner stopped draining the byte-exchange inbox.
- Prompts were limited to 138 tokens on the 8 GB GPU because of the model's CUDA gated-delta fallback memory use (the same with MlxRing).

## Known limits

Pipeline parallelism and text models only; tensor parallelism and image models are rejected at placement; receive reuse is audited only for Qwen3 and the synthetic model; the Metal activity policies are experimental; real-link peer-failure behavior is not injected on hardware.

## Not yet done for a release

A release-candidate run of the suites, a physical rerun at wire protocol 4 if the release process requires it, and a clean-environment install check from release artifacts.
