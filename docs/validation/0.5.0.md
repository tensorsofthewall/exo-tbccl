# exo-tbccl 0.5.0 validation

```{warning}
**This is not a certification.** exo-tbccl 0.5.0 is a security-maintenance minor release of 0.4.0 (TBCCL C ABI 1, wire protocol 4). The adapter source is unchanged apart from the version string, so the adapter evidence of 0.4.0 stands; this page records what is specific to 0.5.0: the new fork pin and the rebuilt wheels.
```

## What changed

The supported exo fork tag moves from `tbccl-integration-v2` to `tbccl-integration-v3`. The two tags have the same integration code; v3 adds the setup helper and the documentation of the line and updates the fork's trust-store dependencies after the October 2026 emSign CA removal (certifi 2026.10.19 in `uv.lock`, webpki-roots and webpki-root-certs 1.0.11 in `Cargo.lock`, uv 0.13.4 or later). The wheels are rebuilt against TBCCL 0.7.1 in a patched build environment. This is not a vulnerability fix of exo-tbccl: none of the 0.4.0 wheels contains a CA bundle or performs TLS.

## The fork pin (framework pin change)

A pin move needs a targeted physical run (maintenance policy). On the immutable tag `tbccl-integration-v3`:

- `uv sync --no-dev --locked --extra mlx-cuda13 --extra tbccl` on Linux x86-64 and `uv sync --no-dev --locked --extra mlx --extra tbccl` on macOS arm64 resolve from the lock, build `exo_rs` with the updated Rust lock and install exo-tbccl 0.3.0; the Linux package set is identical to the v2 environment except for certifi. `uv lock --check` passes and `cargo check --locked --workspace` passes.
- The CI-built 0.5.0 wheels were installed over those environments and run through the two-rank exo pipeline benchmark on the Linux CUDA / Apple Metal pair over a direct Thunderbolt 4 link with `Qwen3-0.6B-8bit` (48 tokens, both orientations, three repetitions each: six launches, all successful). The generated tokens match the single-host reference in every launch, the decode step time was 9.1 to 9.6 ms with the Linux host as rank 0 and 10.7 to 11.1 ms with the Mac as rank 0 (the 0.4.0 evidence recorded about 9.0 and 10.9 ms), and the before/after health snapshots of both hosts show no new kernel events, no stop reasons and zero interface errors or drops. PCIe AER reporting is unavailable on the Linux host, so no statement about AER errors is made.

This is one short generation on one model and one machine pair; it does not establish performance, scalability or recovery.

## Release artifacts

The CI-built wheels, checksums, SBOMs and attestations are verified from the outside with `tools/verify_public_release.py --download` after publication; the result is recorded in the release notes of the GitHub release.
