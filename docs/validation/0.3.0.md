## Phase 75C.5 re-validation (rebased exo integration, MLX 0.32.4 development build on macOS, TBCCL wire protocol 4)

The exo integration was re-derived on upstream exo `75d8ad2bc1eac25aaf7adb39c0784ad0def8c1b6` (2026-10-12) and the Linux CUDA / Mac Metal pair re-qualified over Thunderbolt 4.

- **Defect found and fixed: Metal DLPack convention.** With upstream exo's new macOS MLX pin (0.32.4.dev, `0e3ff3643`) the test suites and the synthetic pipelines crashed the ranks (SIGSEGV/SIGBUS): that MLX exports the `id<MTLBuffer>` handle in the DLPack `data` field, where the 0.32.0 development builds exported the contents address, and the bridge read the handle as an address. The bridge now probes the convention once per process and resolves the handle through `[buffer contents] + byte_offset` (shared storage); anything else raises. See [the bridge](../concepts/bridge.md). The exo-tbccl suite on the Mac: 130 passed, 1 skipped (the documentation test that reads the repository does not apply to a source-free tree), previously 3 failures plus crashes.
- **Test suites.** exo (rebased, default suite): Linux 685 passed, 5 skipped; macOS 687 passed, 3 skipped; the slow synthetic TBCCL pipelines (2 to 4 stages, 8 tests) pass on both. exo-tbccl with the final wheels: see the release checks below.
- **Loopback with the real model.** Qwen3-0.6B-8bit split 21/7 and 7/21, prompts of 49, 577 and 7,201 tokens, default and receive-reuse modes on Linux CUDA (12 runs) and default mode on macOS Metal (6 runs): token ids identical to the unsharded greedy reference in every run, zero payload copies.
- **Real exo cluster, Qwen3-0.6B-8bit, three cycles** (rebased exo on both hosts, Linux CUDA MLX 0.32.0, macOS MLX 0.32.4 development): discovery in 6 to 7 s, 60 s of stable membership (no peer expiration; one master, both nodes agreeing on the same session), `MlxTbccl` placement (21/7 in two cycles, 7/21 in the third), generation of 20-, 374- and 7,390-token prompts token-identical to the reference runs of the release candidate, both hosts executing stages; each rank issued `all_gather` (208), `any_true` (14), `barrier` (9), the sending rank 128 `send_async` and 122 `send`, the receiving rank 128 `recv_into_async` and 128 `recv_like`; both nodes shut down clean (no listeners, no processes); PCIe AER counters and interface errors unchanged.
- **Real exo cluster, Qwen3.8-27B-4bit** (64 layers, with exo's memory override of 5,200 MB on the Linux host and 10,800 MB on the Mac, as before): four starts at wire protocol 4 loaded, prefilled (20 and 138 tokens) and decoded; Mac rank 0 with 43 layers and Linux rank 1 with 21 in the three placements exo chose, and Linux rank 0 with 21 layers and Mac rank 1 with 43 in an explicit instance; 150 `all_gather`, 8 `any_true`, 8 `barrier` and 100 sends/receives per rank; clean shutdown each time. This retires the earlier caveat that the 27-billion-parameter run was recorded at TBCCL wire protocol 3.
- **Transport probe.** `examples/two_host_fastpath.py` between the Linux CUDA rank and the Mac Metal rank after the rebase: five modes, three sizes, 60 iterations each, GPU-produced varying payloads verified bit for bit: all passed.

## Behavior at default settings

On the 27-billion-parameter run the default TBCCL decode median was about 5% slower than exo's MlxRing backend (about 146 versus 139 ms per token); with the opt-in Metal activity policy it was 1 to 4 ms per token faster. Decode there is bound by the Mac's memory bandwidth, not the link (about 30 KB per token). First-token output matched the control except for a documented bf16 near-tie, which flips run to run even under MlxRing; the transport itself was bit-exact.

## Release-candidate wheel checks

The published 0.3.0rc1 wheels (byte-identical to the release assets) were installed into clean virtual environments on a Linux CUDA host and a Mac and exercised over Thunderbolt 4:

- **Transport probe.** Five fast-path modes (baseline, managed, recv, async, combined) between a CUDA rank and a Metal rank, bf16 payloads of 2,048, 8,192 and 16,384 elements, 30 verified iterations each, GPU-produced varying payloads checked bit for bit: all passed.
- **Real exo cluster.** Three complete cycles of exo start on both hosts, discovery, 60 s of stable membership (no peer expiration, one master), `MlxTbccl` placement of Qwen3-0.6B over both hosts, generation of three prompts (20, 374 and 7,390 prompt tokens) and shutdown. All three cycles passed; outputs agree with the earlier single-device, ring and TBCCL reference runs (the medium prompt over its first 32 tokens); in the two cycles instrumented for it, each rank issued `all_gather` (209), `any_true` (14), `barrier` (9), and the Mac the `send`s (250) matching the Linux rank's 128 `recv`s; both hosts shut down clean; PCIe error counters, interface errors and drops unchanged.
- **Discovery.** Earlier attempts at forming the cluster failed because the Mac node was started from a detached tmux session (every discovery send failed with `No route to host`, and exo's discovery then stopped announcing) and because a diagnostic listener on UDP port 52413 took the unicast discovery replies. Neither is a defect of exo-tbccl; both are documented as operational workarounds ([running across two hosts](../guides/two-host.md)).

## Known limits

Pipeline parallelism and text models only; tensor parallelism and image models are rejected at placement; receive reuse is audited only for Qwen3 and the synthetic model; the Metal activity policies are experimental; real-link peer-failure behavior is not injected on hardware.

## Not yet done for a release

The final 0.3.0 release itself (no `v0.3.0` tag, wheels or numbered documentation exist yet); publication of the exo integration that exo-tbccl requires ([compatibility](../reference/compatibility.md)); (the 27-billion-parameter run was repeated at wire protocol 4 in the section above).
